# Minimum-version floors so a transitive minor release can't break
# green-on-main without a commit on our side. Bump when the project
# intentionally adopts behaviour from a newer release. The next-major
# upper bound (`,<N`) protects against API breaks at the major boundary.
# When scaffolding: replace each floor with the version you actually
# develop against — `pip show <pkg>` on a working dev install gives you
# the right starting point.
#
# Floor ordering note: the `pytest-homeassistant-custom-component`
# floor MUST stay compatible with the CI Python pin in
# `.github/workflows/validate.yml`. PHACC 0.13.317+ requires Python
# ≥3.14 and wraps HA core 2026.5+ (which itself requires Python
# ≥3.14.2). The earlier pyo3 0.24 build blocker on 3.14 is gone:
# orjson 3.11.8, Pillow 12.2.0, and pydantic-core 2.46.2 all ship
# cp314 wheels (verified 2026-05-07). Floors below track PHACC
# 0.13.348's transitive `==` pins (pytest-cov==7.1.0,
# pytest-asyncio==1.4.0) — they move with the PHACC floor.
pytest-homeassistant-custom-component>=0.13.348,<0.14
pytest-asyncio>=1.4.0,<2
pytest-cov>=7.1.0,<8
# syrupy floor intentionally omitted: PHACC pins syrupy with `==`, so any
# floor here either matches PHACC (redundant) or contradicts it. A `<6`
# cap in particular becomes UNRESOLVABLE the moment PHACC moves to
# syrupy 6. Let PHACC's transitive pin govern; Dependabot bumps of
# syrupy can't apply anyway.
# Linters/type-checkers are pinned EXACT (== not >=). ruff and mypy add or change
# rules between releases, so a floating range lets an upstream release turn CI red
# with no code change on your side — brutal on a nightly `schedule` run. Pin them,
# and let upgrades arrive as Dependabot PRs whose CI shows the new findings so you
# adopt them deliberately. Use the version from a working install (`ruff --version`,
# `mypy --version`).
#
# Lesson paid for 2026-07: ruff 0.16.0 floated in and broke every repo's nightly
# CI overnight. The pin is what turned that into a scheduled task instead of an
# outage — 0.16.0 was then adopted deliberately on 2026-07-25, on a branch, with
# its ~80 findings reviewed and fixed. That is the whole point of the `==`: not
# to stay old, but to choose when you move.
mypy==2.3.0
ruff==0.16.0
# pycares is no longer relevant: PHACC 0.13.329 pulls in HA core
# 2026.5.0, which pins aiodns 4.x; aiodns 4 uses the pycares 5 API
# natively (no more `ares_query_a_result` reference), so the
# transitive resolver picks pycares 5.x without intervention.

# which imports turbojpeg at module level. In production HA installs it from
# camera's own manifest; the pytest env has no such resolution step, so it
# must be declared here or every test touching the camera platform fails at
# collection.
#
# This pin MUST equal whatever `homeassistant/components/camera/manifest.json`
# requires — currently PyTurboJPEG==1.8.3 on HA 2026.7. It tracks HA core, not
# the newest release: testing against a decoder users never run defeats the
# point of pinning it. Verify with:
#   python -c "import json;print(json.load(open('.venv/lib/python3.14/site-packages/homeassistant/components/camera/manifest.json'))['requirements'])"
#
# Dependabot is told to ignore it (.github/dependabot.yml). It bumped this to
# 2.5.0 once and rewrote the comment above to claim HA required 2.5.0, which
# was false — HA core was still on 1.8.3. Raise it only when HA core does.
PyTurboJPEG==1.8.3
